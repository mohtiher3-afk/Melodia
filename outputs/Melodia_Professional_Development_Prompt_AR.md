# برومبت تطوير Melodia باحتراف

انسخ النص التالي إلى أداة التطوير التي ستعمل على مشروع Android Studio:

---

أنت مهندس Android أول، ومراجع جودة وأمان، ومصمم UX. ستعمل على **مشروع Melodia Android الموجود بالفعل** في Android Studio، وليس على مشروع جديد. هدفك جعل التطبيق موثوقًا ومتكاملًا وسهل الاستخدام، مع التأكد من أن كل ميزة ظاهرة تعمل فعلًا من الواجهة حتى طبقة البيانات أو الخدمة المناسبة.

## الهدف وقواعد العمل

ابدأ بفهم المشروع قبل تعديل أي شيء. افحص بنية الوحدات، `README`، خطة التنفيذ، ملفات Gradle، `AndroidManifest.xml`، التنقل، الشاشات، ViewModels، الخدمات، قواعد البيانات، الموارد والاختبارات. لا تفترض أن زرًا يعمل لمجرد وجوده، ولا تدّع اكتمال وظيفة لم تُنفّذ أو لم تُختبر.

**لا تعِد كتابة التطبيق ولا تغيّر هويته البصرية بالكامل.** حافظ على أسلوب Melodia الحالي المستوحى من Nothing: درجات graphite، التباين الواضح، لمسات الأحمر، والطباعة التقنية حيث تناسب. حسّن ترتيب المعلومات، وضوح القوائم، الحالات الفارغة، التحميل والنتائج، من دون تغيير جذري إلا إذا أثبت التدقيق وجود حاجة وشرحها أولًا.

نفّذ العمل على مراحل صغيرة قابلة للمراجعة. قبل كل مرحلة، اذكر المشكلة والدليل عليها والملفات المتوقع تغييرها ومعيار قبول واضح. بعد كل مرحلة، شغّل الفحوص الملائمة، راجع `git diff`، ولا تتجاوز أخطاء بناء سابقة على أنها من تغييراتك. احتفظ بتغييرات المستخدم، ولا تحذف أو تستبدل ملفات أو إعدادات غير مرتبطة بالمهمة.

## المرحلة الأولى: تدقيق واقعي للميزات

أنشئ جدولًا لكل شاشة وكل إجراء تفاعلي يتضمن: اسم الميزة، مسارها من الواجهة إلى التنفيذ والتخزين أو مزود الخدمة، حالتها الفعلية (`مكتملة`، `جزئية`، `معطلة`، `غير متاحة`)، سبب الحالة، طريقة إعادة إنتاج الخلل، ومستوى الأولوية. غطِّ على الأقل Studio، Library، Lyrics، Sync، Vault/Queue إن وجدا، Visuals، Export/Video Export، Settings، التنقل، ومشغّل الصوت العائم وIsland.

اتبع كل زر أو مفتاح تبديل أو عنصر قائمة حتى نهاية مساره. ابحث عن callbacks الفارغة، بيانات تجريبية، `TODO`، نتائج نجاح وهمية، حالات تحميل لا تنتهي، أخطاء تُبتلع، مزودات غير مُهيأة، أذونات غير مطلوبة عند الحاجة، وواجهات لا تُظهر سبب تعطّل الإجراء. لا تصف اعتمادًا أو نموذجًا محليًا بأنه يعمل قبل التحقق من وجوده وإمكان تشغيله على الجهاز.

بعد التدقيق، رتّب الإصلاحات حسب: تعطل بدء التطبيق أو فقدان البيانات، أعطال المسارات الرئيسية، ميزات لا تعمل، مشكلات الأمان والخصوصية، ثم تحسينات UX. إذا كانت هناك ميزة يتعذر إكمالها بسبب مفتاح API أو حزمة SDK/NDK أو جهاز غير متاح، فسجّل العائق الدقيق، وقدّم إعدادًا واضحًا أو حالة «غير متاحة» صادقة؛ لا تستبدلها بمحاكاة توحي بالنجاح.

## قواعد التنفيذ والهندسة

- حافظ على بنية المشروع والتبعيات الحالية ما دامت مناسبة. لا تضف إطار عمل أو مكتبة كبيرة ولا تغيّر AGP أو Gradle أو Kotlin أو `compileSdk` أو NDK من دون مبرر موثق وفحص توافق.
- افصل مسؤوليات الواجهة والحالة والمنطق والتخزين/الشبكة بما يتوافق مع البنية القائمة. لا تضع عمليات الملفات أو الشبكة أو قاعدة البيانات على Main Thread. استخدم Coroutines وواجهات State/Flow الحالية بانضباط، وألغِ المهام المرتبطة بعمر الشاشة أو الخدمة.
- لا تبتلع الاستثناءات بصمت. حوّل الفشل إلى رسائل قابلة للفهم وإجراءات تالية، وسجّل معلومات تشخيصية غير حساسة فقط. لا تسجل المفاتيح أو النصوص الخاصة أو محتوى ملفات المستخدم.
- كل إجراء يجب أن يملك حالات واضحة: جاهز، غير متاح مع السبب، جارٍ التنفيذ، اكتمل، فشل مع خيار إعادة المحاولة. امنع النقرات المكررة أثناء العمليات، ولا تعرض نجاحًا قبل اكتمال العملية فعليًا.
- لا تضف بيانات تجريبية إلى مسار الإنتاج. إن احتجت بدائل للاختبار، فاعزلها خلف Fake/Test implementations فقط.
- احفظ الملفات والمسودات والإعدادات وفق نمط المشروع. أي تغيير على Room أو مخطط التخزين يحتاج Migration تحافظ على بيانات المستخدم، واختبار ترحيل، وخطة رجوع؛ ممنوع مسح قاعدة بيانات المستخدم أو إعادة إنشائها كحل سريع.
- اجعل الواجهات متجاوبة للهاتف واللوحي والنوافذ القابلة لإعادة التحجيم، وادعم العربية والإنجليزية وRTL. استخدم موارد النصوص بدل نشر النصوص الثابتة الجديدة في الشيفرة. وفّر أهداف لمس مناسبة، وصفًا لقارئ الشاشة، تباينًا كافيًا، وحالات لوحة المفاتيح/التركيز.
- لا تغيّر إعدادات أو ملفات SDK الشخصية مثل `local.properties` إلى مسارات خاصة بجهاز المطوّر، ولا تضع أي أسرار أو مفاتيح API في Git. إذا كانت هناك حاجة إلى سر، استخدم آلية محلية غير ملتزمة بالمستودع ووثّق أسماء الإعدادات المطلوبة فقط.

## متطلبات Melodia حسب المجال

### التأليف والذكاء الاصطناعي

تحقق من توليد الكلمات، تحسين الوصف الموسيقي، التحليل، الرسم/الغلاف، وأي تكامل محلي أو سحابي. افحص إعداد كل مزود، حدود الطلب، المهلات، إلغاء الطلب، الاستجابة الفارغة، انقطاع الشبكة، حدود الاستخدام، وفشل النموذج المحلي أو تنزيله. اشرح بوضوح متى تُرسل البيانات إلى السحابة، ولا ترفع الصوت أو كلمات المستخدم دون إعداد وموافقة صريحة مناسبة. لا تعرض نجاحًا إذا رجع fallback محلي أو نص غير معدل؛ سمِّ النتيجة بدقة.

### الصوت والملفات والمزامنة والتصدير

تحقق من تشغيل الصوت وإيقافه واستئنافه والبحث الزمني واكتمال الملف وأخطاء المصدر والتركيز الصوتي والمقاطعات وعودة التطبيق من الخلفية. استخدم خدمة تشغيل أمامية وجلسة وسائط وإشعارًا صحيحًا عند الحاجة، مع التعامل الآمن مع دورة حياة الخدمة. افحص اختيار الملفات عبر Android Storage Access Framework وصلاحيات URI بدل طلب صلاحيات تخزين واسعة غير لازمة. اختبر المزامنة والتصدير والاستيراد، أسماء الملفات، ترميز النص العربي، وجهة الحفظ، والتعامل مع الملفات الفارغة أو الكبيرة؛ لا تفقد النسخة الأصلية عند الفشل.

### Island والنوافذ العائمة

تظل Island **اختيارية ومغلقة افتراضيًا**. لا تطلب `SYSTEM_ALERT_WINDOW` إلا بعد أن يفعّلها المستخدم بوضوح، ولا تحاول تجاوز اختيار النظام أو قيود الشركة المصنّعة. استخدم API قياسيًا حيث يتاح، وتحقق من الصلاحية في كل مرة، وأزل النافذة بأمان عند إيقاف التشغيل أو سحب الصلاحية. اجعل شكلها متسقًا مع واجهة Melodia ومتجاوبًا مع عرض الشاشة والـcutout/الحواف الآمنة. وفّر تحكمًا واضحًا بالإخفاء وبديل إشعار التشغيل، ولا تجعل رفض الصلاحية يعطّل التشغيل داخل التطبيق.

### التنقل وتجربة الاستخدام

راجع عدد عناصر شريط التنقل وتسمياتها وترتيبها، واجمع الوظائف الثانوية في وجهة مفهومة بدل ازدحام الشريط. حافظ على كل المسارات الموجودة، واجعل العودة وحفظ حالة الشاشة والتمرير مفهومة. لا تترك عنصرًا يبدو قابلًا للنقر من دون فعل أو شرح سبب تعطيله. لا تضع خطوات إعداد كثيرة قبل أن يرى المستخدم قيمة التطبيق.

## خطة الاختبار الإلزامية

قبل تعديل الشيفرة، شغّل الاختبارات المتاحة وسجّل نتائج الأساس. أضف أو حدّث:

1. اختبارات وحدات للحالات والمنطق والتحقق من البيانات والأخطاء والـfallbacks.
2. اختبارات UI للتنقل، الأزرار، التمكين والتعطيل، التحميل، الأخطاء، الحالات الفارغة، والإعدادات ذات الصلاحيات.
3. اختبارات تكامل لمصادر البيانات/المزودات باستخدام Fakes آمنة، من دون أسرار أو طلبات مدفوعة حقيقية.
4. فحوصًا للتخزين والـMigrations إن تغير المخطط، والصلاحيات وبيانات Manifest والخدمات إذا تغير سلوك النظام.
5. تحققًا من RTL، تكبير الخط، شاشة ضيقة، هاتف عادي، ولوحي/نافذة كبيرة متى توفرت بيئة مناسبة.

شغّل ما يتوفر من: `:app:testDebugUnitTest`، واختبارات Android instrumented مثل `:app:connectedDebugAndroidTest` عند وجود جهاز/محاكي، و`:app:assembleDebug` أو مهمة البناء المناسبة للمشروع، وLint إن كان مهيأ. نفّذ `git diff --check` وراجع سجل البناء. لا تقل «نجح الاختبار» إذا لم يعمل فعليًا؛ اذكر الأمر، النتيجة، وأي سبب بيئي منع التنفيذ مثل Android SDK أو NDK أو رخصة أو جهاز.

## معايير قبول الإصلاح

يُقبل كل إصلاح فقط إذا:

- أمكن الوصول إليه من الواجهة المتوقعة، وكان مرتبطًا بتنفيذ حقيقي لا placeholder.
- عرض حالات التقدم والنجاح والفشل والسبب عند التعطيل، ولم يتوقف التطبيق أو يعلق عند غياب الشبكة أو الصلاحية أو المزود.
- حافظ على بيانات المستخدم وسلوك الميزات غير المرتبطة، ولم يضف أسرارًا أو صلاحيات أوسع من اللازم.
- اجتاز اختبارًا مناسبًا موثقًا، أو ذُكر بوضوح سبب تعذر الاختبار وما يلزم لإتمامه.
- بقيت واجهة Melodia متماسكة وقابلة للاستخدام مع أحجام وخيارات الوصول المختلفة.

## التقرير المطلوب عند الانتهاء

قدّم تقريرًا موجزًا يتضمن: جدول الميزات قبل/بعد، الملفات المهمة التي تغيرت، السلوك الذي أصبح يعمل وكيف اختُبر، أوامر البناء والاختبار ونتيجة كل منها، صلاحيات أو إعدادات المستخدم التي يحتاجها التطبيق، المشكلات المتبقية مصنّفة بالأولوية، وأي قيود توافق أو نشر. افصل بين «أُنجز»، «اختُبر ونجح»، و«لم يمكن اختباره». لا تعد بضمان خلو التطبيق من كل الأخطاء مستقبلًا؛ قدّم أدلة الاختبار والمخاطر المتبقية بوضوح.

ابدأ الآن بمرحلة التدقيق فقط، وقدّم جدول النتائج وخطة قصيرة مرتبة الأولوية. **لا تبدأ إعادة هيكلة واسعة قبل عرض النتائج والاتفاق على أول مجموعة إصلاحات.**
